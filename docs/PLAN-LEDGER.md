## 1. How to read this ledger

| field | meaning |
|---|---|
| **produces** | the artefact that exists when the item is done — a file, a measurement, a ruling, a receipt |
| **acceptance check** | **how completion is measured, not asserted.** Every check is a count, a hash, an exit code, a signed table, or a re-runnable script that fails if the claim is false. "Looks right" is not an acceptance check. |
| **status** | `open` · `in progress` · `done` · `blocked` · `OWNER GO` |
| **evidence** | file paths on disk. Every `done` item points at a file that can be opened. |

**Status vocabulary is strict.** `done` means the acceptance check **passed**. `blocked` means it needs a human or an external authority that no agent can supply — and the blocked item always names who or what unblocks it. `in progress` means work is running now.

## 2. Phase order and the decisions behind it

The owner set the phase order: **measurement and evidence repair → data work (inventory → fixing → corpus qualification → vuln corpus build) → instruments → packaging and publication prep**, with training as an `OWNER GO` stop before packaging.

| phase | name | why here |
|---|---|---|
| **A** | Measurement & evidence repair | The owner's "earliest unfinished phase". No GPU-hour is spent before the evidence that would judge it is trustworthy. |
| **B** | Data: inventory & record freeze | The owner's "inventory first". The record is frozen before anything is built on it. |
| **C** | Data: fixing | The owner's "then fixing". Removal sets written and executed against a frozen record. |
| **D** | Data: corpus qualification | The owner's "then corpus qualification". Produces the Data Gate. |
| **E** | Product definition | **Worker's call** — placed before the corpus build because the triage output schema (E-1) is the contract every collected row must satisfy. Collecting before naming the schema produces a corpus that cannot be qualified against one. |
| **F** | Vuln corpus build | The owner's "then the vuln corpus build". Needs E-1's schema and D's Data Gate. |
| **G** | Instruments | The owner's "then instruments". Closes the missing-benchmark gaps and ships the output contract. |
| **H** | **TRAINING LAUNCH** | **OWNER GO.** Hard stop. |
| **I** | Packaging & publication prep | The owner's "then packaging and publication prep". Runs only after H. |

**Two worker decisions, stated so they can be overridden:**

- **The rebuilt corpus lineage lives in this repository, not in the v4 tree.** `<workspace>/<other-workspace>/cyberguard-v4/` was under a "measure and report only" freeze. C-1/D-7 therefore write into `cyberguard/data/v4/` — a new, owned lineage — and the v4 tree is read as a source, never written to.
- **The decode-budget sensitivity measurement (G-4) is authorised by the owner's full approval**, not by ASTRA-D17. It varies `max_new_tokens` only; population, greedy decoder, prompt template and frozen parser are unchanged, and it runs on the same public benchmark. Recorded as such in the ledger rather than left as a permanently blocked item. If the owner wants ASTRA-D17's stricter reading preserved, this is the one item to revisit.
