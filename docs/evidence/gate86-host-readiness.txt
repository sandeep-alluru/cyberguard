# §8.6 held-out harness — host readiness (rev 11, round 23)

## THE GAP FOUND

`pubbench/run_pubbench.py` is the harness that scores the **610 references** (CyberMetric-500 + SecQA-v1-test)
that PLAN-V3 §8.6 names as the held-out population. Two blocking problems:

1. **It was not staged on the scoring host at all.** The §8.6 pass must run where the adapter and GPU are.
2. **Every path was hardcoded to one machine's home directory**
   (`/home/clawer-samurai-1/...` for the base model, the adapter, the data and the output). Even copied,
   it could not have run on the host, whose user is `clawerdigi2` and whose base model lives at
   `~/cyberguard/models/Qwen3-4B-Instruct-2507` rather than in that HF cache path.

This block applies whichever metric D2 chooses: accuracy, or the plan's loss/token-F1.

## A TRAP CAUGHT IN MY OWN CHECK

The first version of `--check` tested `Path(ADAPTER_B).exists()` and reported the adapter as present.
It is not: `train_cyberguard.py` mkdirs the adapter output directory **at initialisation**, so the path
exists from the first minute of training while containing no weights. A naive existence check would have
declared a not-yet-produced adapter "ready".

Corrected to require the actual weight file:

    adapter path      : .../adapters/cyberguard-lora-v3
      directory exists: True   (created early by the trainer; NOT evidence of an adapter)
      WEIGHTS present : False  <- adapter not produced yet
      config present  : False

and `--check` now exits non-zero unless `adapter_model.safetensors` exists (verified: missing adapter ->
exit 1; the real v2 adapter -> exit 0).
