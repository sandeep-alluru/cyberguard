# Post-training path readiness — harvest (rev 11)

tools/harvest-v3.sh retrieves every v3 artifact with a per-file transfer and a remote-vs-deposited
sha256 comparison, and refuses to print HARVEST-COMPLETE unless every hash matched. It follows
harvest-v2.sh and the lessons that file's own comments record:
  - one file per transfer (CRAFT-O-05: a multi-path scp silently fetches nothing);
  - THE ADAPTER IS PULLED EXPLICITLY. v2's harvest described itself as 'every artifact' while
    omitting the adapter - the one artifact the run exists to produce - so a verifier reading the
    manifest could not find the model;
  - the DEPOSITED copy is compared against the REMOTE hash, never the source against itself;
  - dry-run by default, so it can be inspected before anything is transferred.

Artifacts covered: the training receipt (receipts/cyberguard-lora-v3.json), the adapter
(adapter_model.safetensors + adapter_config.json), the training log, the exact mixture that was
trained, all 14 registered batteries x {base, armB}, the assembled gate inputs, and the verdict.

DRY RUN against the live host (training still running, so this is the expected pre-completion state):
  ABSENT  receipts/cyberguard-lora-v3.json          <- written by the trainer at the end
  ABSENT  adapters/cyberguard-lora-v3/*             <- written by the trainer at the end
  PRESENT logs/train-cyberguard-lora-v3.log         sha=45047dd8f2da3deb...
  PRESENT data/v3/mixture/mixture-v3-no-trail.jsonl sha=75b5099c568313f2... <- MATCHES the reviewed
                                                                              mixture by hash
  ABSENT  evals/battery-*.json                      <- not run yet (no adapter)

The mixture hash is a useful independent cross-check: the corpus the training host actually holds is
byte-identical to the artifact this plan reviewed and pinned. So the run's inputs are confirmed again,
from the receiving side, at a different time.

The receipt itself is written by the trainer (train_cyberguard.py writes receipts/<RUN_NAME>.json at
the end of training, containing the loss curve, step timing, token count, library versions and the
held-out split) - so there is no separate harvest step to get wrong.

## POST-TRAINING RUNBOOK (rev 11) — with a measured cost estimate

The §8 scoring phase is ~1.5 h of GPU work, so it should be executed from a runbook rather than
improvised. Every step below has been dry-run or verified this session.

STEP 3 — score the candidate and its base reference (the long step)

  *** CORRECTED 2026-10-01 after an Astra readiness review. Two defects here would have wasted the pass. ***

  DEFECT 1 — WRONG ARM LABEL. This step used to generate the v3 adapter as `--arm armB`. But the
  assembler takes the REGISTERED gate decisions from `armA`
  (v2/assemble_gate_inputs.py: gC/gF/gB/gE/gA2/gJ all read ("...", "armA")), and its own comment says Arm
  B is "observational only — they inform the report; the registered decisions remain Arm A's gates".
  v3 is a SINGLE-ARM run: there is no second arm. The one adapter IS the candidate, so it must occupy the
  candidate slot `armA`. Generating armB would have left every registered gate unmeasured and thrown away
  the whole GPU pass.
  DEFECT 2 — SecQA SILENTLY UNSCORED. `eval_cyberguard.py` generates answers only for `rows[:N_GEN]`, and
  N_GEN defaults to 500. The v3 loader lists all 500 CyberMetric rows FIRST, so at the default the entire
  110-row SecQA half receives no generated answer and §8.6's per-dataset block would be half-missing.
  Verified by running the loader: first 500 rows = {'cybermetric-500': 500}. Set N_GEN=610.

    ADAPTER=$HOME/cyberguard/adapters/cyberguard-lora-v3
    export N_GEN=610                     # REQUIRED — 610 covers CyberMetric-500 + SecQA-110
    export RUN_NAME=cyberguard-lora-v3   # REQUIRED — unset defaults to the v1 adapter
    for b in gA fresh-gA gA2 gB gC gE gF gG-gsm8k gG-ifeval gJ fresh-gB fresh-gE fresh-gF fresh-gJ; do
      python3 v2/run_battery.py --battery $b --arm base --out ~/cyberguard/evals
      python3 v2/run_battery.py --battery $b --arm armA --adapter "$ADAPTER" --out ~/cyberguard/evals
    done
  `--adapter` IS MANDATORY ON THE TUNED ARM. It defaults to None, and `eval_cyberguard.load(path, None)`
  loads the BASE MODEL -- so the tuned arm without `--adapter` writes a receipt LABELLED armA that contains
  base-model outputs, with `"adapter": null` in its provenance. Because every paired gate compares the
  candidate against base, that makes delta = 0 and G-A's "lower bound > -0.10" would PASS: a FALSE PASS on
  the central safety gate, produced entirely by an omitted flag.
  ASSERT IT AFTER THE RUN (fail-closed):
      python3 - <<'PY2'
      import glob, json, sys
      bad = []
      for f in glob.glob("$HOME/cyberguard/evals/battery-*.json"):
          d = json.load(open(f))
          if d.get("arm") == "armB" and not d.get("adapter"):
              bad.append(f)
          if d.get("arm") == "base" and d.get("adapter"):
              bad.append(f)
      print("MISLABELLED RECEIPTS:", bad)
      sys.exit(1 if bad else 0)
      PY2
  Any armB receipt with a null adapter is NOT a tuned measurement; any base receipt carrying an adapter is
  not a base measurement. Both invalidate the comparison.
  COST ESTIMATE (measured rate 0.523 s/sample, 4,840 registered probes per arm):
      4,840 probes x 2 arms = 9,680 generations  ->  ~5,063 s  =  ~84 min
  Plus §8.6 held-out via pubbench (~3.3 min/arm measured)   ->  ~7 min
      TOTAL §8 SCORING  ~91 min (~1.5 h)

STEP 5b — COMPOSE THE VERDICT DOCUMENT (this step was MISSING from the runbook)
    python3 v2/write_verdict_v2.py --version v3 --report ~/cyberguard/evals/gate-report-v3.json \
        --evals ~/cyberguard/evals --out ~/cyberguard/docs/VERDICT-v3.md
  `--version v3` IS MANDATORY. Without it the composer defaults to v2 and would cite the v2 adapter's
  training receipt and v2's mixture while presenting them as the v3 verdict -- a narrative about the wrong
  run (Astra readiness review, defect 3). With `--version v3` it reads receipts/cyberguard-lora-v3.json
  and v3/data/mixture/FACTS.json, and renders ONE arm, because v3 is a single-arm run: the v2 A-vs-B
  Claim 2 contrast is not applicable and is stated as such rather than fabricated.
  The gate report is not the verdict: `write_verdict_v2.py` composes the VERDICT document from the report
  and the harvested manifest, and labels every gate by instrument role (retained/training-row instruments
  are marked RECALL, never generalisation). It is FAIL-CLOSED: it REFUSES to write a verdict when the
  report contains a CONTRACT abort row or when no gate reached PASS/FAIL. Verified on the stub report:
      "FATAL: no gate reached PASS or FAIL - an all-UNMEASURED report is not a verdict"  (exit 1)
  Exit 0 means the verdict was written; anything else means it was not, and there is no verdict to report.
  Present and hash-identical on the host (no staging needed).
