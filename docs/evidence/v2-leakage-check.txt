# Can v2 artifacts leak into the v3 verdict? — checked, mitigated (rev 11, round 15)

Motivated by D8 (the assembler silently substituting stale v1 measurements). If an aggregate fallback
could do that, could the **per-probe battery** path likewise pick up a previous window's receipts? The
training host already carries v2 artifacts, so this was worth checking rather than assuming.

## THREE INDEPENDENT GUARDS, ALL VERIFIED

**1. The host's eval directory is effectively empty of v3-relevant JSON.**
```
~/cyberguard/evals/  ->  0 top-level .json files
                         cyberguard-lora-v1.partial.json.batch1-old   (does not end in .json -> skipped)
                         .pre-c24-archive/                            (a SUBDIRECTORY)
```
`classify_evals()` iterates `os.listdir(d)` and therefore is **non-recursive**, so the archive's v2
receipts (`cyberguard-lora-v2-armA.json`, `merge-equiv-cyberguard-lora-v2-armA.json`, ...) are never
enumerated. The stray file fails the `fn.endswith(".json")` filter. Verified on the host directly.

**2. The identity guard is enforced, not decorative.** `gates_v2.py` (review F17) forces a
battery-derived gate to UNMEASURED when the receipts for an arm disagree on adapter/base-model/decode
surface, or when no receipt recorded an adapter sha256 at all:
```
if not _ident.get("consistent", True):      _ident_bad = "... do not agree on the tested adapter/decoding surface"
elif not _ident.get("has_adapter_hash", True): _ident_bad = "no battery receipt ... recorded an adapter sha256,
                                                            so the measurement cannot be attributed to a checkpoint"
...
if _ident_bad and gid in _battery_gates:
    row["outcome"] = "UNMEASURED"; row["unbound_identity"] = True
```
VERIFIED by running the chain: **4 gates carried `unbound_identity=True`** (G-A co-secondary, Claim 1,
G-A refusal retention, Claim 2). The guard fires.

**3. Stub inputs are flagged and never decided.** Review F17 also records that a `--stub` battery
"exercises the plumbing and never the model, yet a stub chain produced gate decisions". The guard sets
`stub_input=True` and forces UNMEASURED. VERIFIED: **4 gates carried `stub_input=True`** in the same run,
and the stub battery receipt itself carries `"stub": true`.

## CONCLUSION

No actionable defect here. The aggregate-fallback hole (D8) was real and is now fixed; the per-probe
path was already protected by an identity binding that refuses to attribute a measurement to a
checkpoint it cannot name, and by a stub flag that refuses to decide on synthetic input. Reported as
checked-and-clean rather than dressed up as a finding.

The residual risk is narrow and inherent: if the v3 batteries ran but wrote **no adapter hash**, the
identity guard would mark their gates UNMEASURED rather than mis-attribute them — a false negative
(lost measurement), not a false positive (wrong verdict). That is the correct direction to fail.
