## 4. THE RUNBOOK WAS MISSING THE VERDICT STEP (round 32)

The §8 run does not end at the gate report. The formal deliverable is composed by
`v2/write_verdict_v2.py`, which reads the gate report plus the harvest manifest and writes the VERDICT
document, labelling every gate by instrument role (retained training-row instruments marked RECALL, never
generalisation). My runbook stopped at `gates_v2.py`, so following it would have produced measurements but
no verdict.

Verified rather than assumed:

    python3 v2/write_verdict_v2.py --report <stub report> --evals <dir> --dry-run
    -> "FATAL: no gate reached PASS or FAIL - an all-UNMEASURED report is not a verdict"   exit 1

which is the correct fail-closed contract: "Exit 0 only when the verdict was written". An all-UNMEASURED
run (exactly what the stub chain produces) must never yield a verdict, and it does not.

Freshness checked: the script is present on the host and hash-identical to the local copy, so no staging
step was needed — the gap was in the runbook, not the deployment.

The runbook now has STEP 5b for it, with the exit-code contract stated so a reader cannot mistake a
refused verdict for a silent success.

## 5. A SECOND RUNBOOK GAP — AND IT IS THE EXACT v1-DEFAULT FOOTGUN (round 33)

`eval_cyberguard.py` resolves the adapter it scores as:

    ADAPTER = ROOT / "adapters" / os.environ.get("RUN_NAME", "cyberguard-lora-v1")

The default is **`cyberguard-lora-v1`**. My runbook's §8.6 step read `python3 eval_cyberguard.py` with
**no RUN_NAME** — so following it would have scored the **v1 adapter** and filed the result under v3's
§8.6. That is precisely the failure SPEC-V2 records in its own notes:

    "The row previously cited `--run v2`, a flag this script does not have (it takes no flags and reads
     RUN_NAME from the environment, so the flag was silently ignored and the run defaulted to the v1
     adapter)"

A documented, previously-suffered false-verdict path, reintroduced by an incomplete runbook. Found by
auditing the runbook against the script rather than trusting the runbook.

### FIXED, TWO WAYS

1. **The script now announces the default.** When `RUN_NAME` is unset it prints, to stderr:
       WARNING: RUN_NAME is unset -> scoring adapter 'cyberguard-lora-v1' (the HISTORICAL DEFAULT).
                If you meant the v3 adapter, re-run with RUN_NAME=cyberguard-lora-v3.
   The default is deliberately KEPT (not removed) so existing v1/v2 invocations stay reproducible — the
   missing thing was the announcement, not the default. Verified: warning fires, and the selected adapter
   is named.

2. **The runbook now sets it and asserts the result.** The step reads
   `RUN_NAME=cyberguard-lora-v3 python3 eval_cyberguard.py`, and is followed by an assertion on the
   receipt:
       assert r['run'] == 'cyberguard-lora-v3', 'WRONG ADAPTER SCORED: ' + r['run']
   A receipt whose `run` field is not exactly `cyberguard-lora-v3` is NOT a v3 measurement, whatever else
   it contains.

Verified with RUN_NAME set: adapter `cyberguard-lora-v3`, receipt `cyberguard-lora-v3.json`.
(`CYBERGUARD_HELDOUT=v3` remains required separately for the 610-reference population.)
Staged to the host: `eval_cyberguard.py 6a924cbde4e0`.

## 6. THIRD RUNBOOK GAP — AND IT WOULD HAVE PRODUCED A FALSE PASS (round 34)

My battery loop omitted `--adapter` on the tuned arm:

    for b in ...; do for a in base armB; do
      python3 v2/run_battery.py --battery $b --arm $a --out ~/cyberguard/evals     # <-- no --adapter
    done; done

`--adapter` defaults to `None`, and `eval_cyberguard.load(model_path, None)` attaches no adapter —
it loads the **BASE MODEL**. The receipt is still written with `"arm": "armB"` and `"adapter": null`.

CONSEQUENCE, and it is the worst of the three: every paired gate compares armB against base. If armB IS
base, then delta = 0 everywhere, and G-A's rule is "Newcombe 95 % lower bound on delta > -0.10" — which
**0 satisfies**. So the chain would have reported a PASS on the central safety gate while having measured
nothing at all. The false-verdict paths found in rounds 32–33 (missing verdict stage, wrong adapter by
RUN_NAME) were silent; this one is silent AND flattering.

The dry run shows exactly why it is easy to miss — without `--adapter` the banner reads:

    model   : armB                                  <- looks fine, loads the BASE model
    model   : armB + .../adapters/cyberguard-lora-v3   <- with --adapter

### FIXED

1. The loop now passes `--adapter $HOME/cyberguard/adapters/cyberguard-lora-v3` on the tuned arm.
2. A **fail-closed assertion** follows the run: any `armB` receipt with a null adapter, or any `base`
   receipt carrying an adapter, aborts. Verified on synthetic receipts: the mislabelled armB is detected
   and the check exits non-zero.

THREE CONSECUTIVE ROUNDS of auditing the runbook against the chain have now found three defects, each of
which would have produced plausible-looking but wrong results. The runbook is code and needs the same
execution-verification as the scripts it calls.
