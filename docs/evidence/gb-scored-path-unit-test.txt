# The G-B score-capture path is now executed (rev 11, round 38)

## WHY THIS WAS THE LAST REAL RISK

`eval_cyberguard.generate_batch_scored` is the code that captures P(malicious) vs P(benign) at the first
decision token — the mechanism that gives G-B its required ranking ROC-AUC. It was written in round 22 and
**had never executed once**, because it needs the model and the GPU is occupied by training.

That is the worst place for an unexecuted path: a shape or index bug (e.g. a row/column transpose when
reading `scores[0]`) would surface only after the ~26-hour run, at the moment grading begins, and would
silently produce wrong AUC values rather than an error.

## EXERCISED WITH A MOCK (no GPU, no weights)

A fake model/tokenizer makes every dimension explicit: vocabulary 50, `malicious`=10, `benign`=11, batch of
2, and first-step logits deliberately asymmetric between rows (row 0 favours malicious 9:1, row 1 the
reverse). A transpose or off-by-one would swap or shift the results.

    texts  : ['malicious', 'malicious']        (decoded from sequences[plen:], correct slice)
    scores : [0.9997, 0.0003]                  (row 0 -> malicious, row 1 -> benign)

  * **row -> score mapping correct (no transpose): True**
  * the mock also asserts the call requests `output_scores=True, return_dict_in_generate=True`
  * a model returning `scores=()` yields `[None]` — an unresolvable score is never fabricated as 0.5

`SELF-TEST: PASS`

## WHAT THIS DOES AND DOES NOT ESTABLISH

Establishes: the plumbing — indexing, slicing, per-row mapping, the empty-scores guard, and the assertion
that scores were requested. Those are the mechanical failure modes.
Does NOT establish: that the real model's first-token distribution is a good ranking signal. That is a
property of the model and can only be measured post-training, which is what the AUC value will report.

Incidentally this run also re-confirmed the round-33 guard: importing `eval_cyberguard` without `RUN_NAME`
prints the v1-default warning to stderr.
