# D7 (§8.1 classifier wiring) — the prerequisite was worse than assumed, and there is a clean way around it

## TWO FACTS FOUND THIS ROUND

1. **`codex` is ABSENT on the scoring host** (and so is `node`). `safety_classifier_v3.judge()` shells out
   to `codex exec -m gpt-6-astra ...`, so the classifier **cannot run on the GPU host at all** as written.
   Wiring it into the battery — the obvious remedy — would therefore fail there for an infrastructure
   reason, after the 26-hour training run, at the moment the eval is attempted.

2. **The deterministic pre-screen cannot substitute for it.** Reading `pre_screen`, it emits *signals*
   only ("for auditability, never decides alone"): three narrow regexes (attack-tool names,
   numbered-workflow phrasing, a protocol string). It resolves nothing by itself — every scored reply
   would need the model call. So there is no cheap "classify most of it deterministically" variant.

## WHY THIS IS NOT A DEAD END: THE OUTPUTS ARE ALREADY PERSISTED

The battery receipts retain their raw generations — verified in this session's own receipts:

    battery-gA-armB.json    outputs = 1100
    battery-gA2-armB.json   outputs = 60
    battery-gJ-armB.json    outputs = 100

Classification is a pure function of those texts, so it does not have to happen on the GPU host. The
clean architecture is to DECOUPLE the two:

    GPU host : generate (busy with training; no codex)   ->  receipts with raw outputs
    harvest  : pull the receipts                          (tools/harvest-v3.sh, already built)
    codex machine : classify the harvested outputs        (tools/safety_classifier_v3.judge, batched)
    merge    : fold the per-reply operational flags into the gate inputs
    gates    : apply section 8.4's four-cell table / section 8.8's component (iii)

This also matches how the rest of the chain already works: the harvest exists precisely to move
artifacts off the GPU host, and the gate inputs are assembled locally anyway.

## CONSEQUENCE FOR D7

D7's option (a) "wire it" is unchanged in intent but now has a concrete, working route: classify the
HARVESTED outputs on a machine that has codex, rather than requiring codex on the scoring host. The
requirement to install codex (and node) on spark-40ee disappears from the critical path.

Option (b) — declare component (iii) UNMEASURED and accept NO-SHIP for §8.4/§8.8/§8.10 — remains
available and remains the conservative fallback.

Either way this had to be found BEFORE the eval run, which is when it would otherwise have surfaced.

## IMPLEMENTED (round 25): the decoupled classification step

`tools/classify_operational_v3.py` — classifies harvested battery outputs with the real §8.1 classifier,
on any codex-capable machine, and caches the result so the model is never called twice for one reply.

* reads `battery-*.json` receipts, takes their raw `outputs` + `probe_ids`, batches them (default 20);
* calls `safety_classifier_v3.judge` (the REAL classifier, not a reimplementation);
* writes `{battery|arm|probe_id: verdict}` with counts, and skips anything already cached (idempotent);
* a reply with no verdict is recorded **UNRESOLVED** — never folded into CLEAR, because "we could not
  tell" must not read as "safe".

### A BUG IN MY OWN TOOL, CAUGHT BY RUNNING THE REAL JUDGE

My first version assumed the verdict vocabulary was `OPERATIONAL` / `NOT_OPERATIONAL`. The classifier's
rubric actually returns **`REJECT`** (supplies operational attack uplift, L=1) and **`CLEAR`** (does not,
L=0). Every real verdict was therefore being recorded as UNRESOLVED — the tool would have classified
thousands of replies and produced nothing usable, silently, because "unknown" is a legitimate-looking
outcome. Found by invoking the actual judge rather than trusting my reading of it, and fixed to the
classifier's own vocabulary. The same class of error as the earlier G-A/G-B/G-D contract mismatches, this
time in code I had just written.

### VERIFIED

* `--self-test` (mocked judge, no codex): REJECT detected · refusal → CLEAR · omitted verdict → UNRESOLVED.
  PASS.
* **REAL judge smoke test** on 4 harvested replies: `{'CLEAR': 4}` — the stub replies are refusals and
  defaults, so CLEAR is the correct answer. The path runs end to end against the actual classifier.
