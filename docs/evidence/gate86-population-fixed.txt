# §8.6 — the held-out loader now serves the 610 references (rev 11, round 24)

## WHAT WAS ACTUALLY WRONG

Cycle 3 found that the §8.6 evaluator "loads the old 500-row Trendyol split". The important refinement
found this round: **the metrics were never missing.** `eval_cyberguard.py` already implements exactly
what §8.6 specifies — `held_out_loss()` (mean NLL over the assistant turn, chat-templated, with a
prefix/mask check) and reference token-F1 via `tok_f1()`, reported as `held_out_loss` and
`ref_token_f1_mean` per arm. §8.6's margins (loss Δ ≤ 0.0, token-F1 Δ ≥ −0.02) were written for it.

The single defect was the **loader**: `load_held_out()` called `cgdata.make_split(...)` on the Trendyol
corpus and returned 500 rows. So the correct machinery was measuring the wrong population. This made D2
look like "choose between accuracy and a metric nobody implemented" when it is really "point the existing
loader at the specified population".

## CHANGED

1. `load_held_out_v3()` — builds the **610 references** (CyberMetric-500 = 500, SecQA-v1-test = 110) in
   the SAME `{system, user, assistant}` shape `held_out_loss` already consumes, plus a `dataset` key. The
   reference answer is `"<LETTER>. <option text>"`, so token-F1 compares against a substantive reference;
   a bare letter would make F1 indistinguishable from accuracy.
2. `load_held_out()` now **dispatches**: `CYBERGUARD_HELDOUT=v3` → the 610 references; default (`v2`) →
   the historical Trendyol split, so an unmodified invocation still reproduces v2 exactly.
3. Per-dataset reporting — §8.6 requires "the pooled metrics AND each dataset independently"; pooled-only
   reporting could not express that rule at all. The receipt now carries a `per_dataset` block with
   per-dataset rows, base/tuned loss, loss_delta, passes_loss_margin, base/tuned token-F1, f1_delta and
   passes_f1_margin.
4. Generated texts are now accumulated (`b_texts`/`t_texts`) so the per-dataset F1 pairs each generated
   answer with the row it came from; previously only the SCORES were kept.

## VERIFIED

* Loader, locally and ON THE HOST: **610 rows = 500 `cybermetric-500` + 110 `secqa-v1-test`**, keys
  `[assistant, dataset, system, user]`, sensible prompts (multi-choice instruction + options) and
  references (e.g. `"A. Permanent"`).
* `python3 -c "import ast; ..."` clean; module imports clean on the host with the v3 dispatch active.
* Staged and hash-verified to spark-40ee.

## VERIFICATION LIMIT — STATED, NOT GLOSSED

The **per-dataset runtime path is NOT executed**: it needs the model, and the GPU is occupied by the
training run. Its syntax and structure have been reviewed and the loader it depends on is verified, but
"the loader returns 610 rows" is not the same claim as "the per_dataset block computes correct numbers".
The post-training runbook therefore adds an explicit check: the v3 receipt MUST contain a `per_dataset`
block with both datasets present, and the pooled-plus-per-dataset rule is applied only if it does.

A bug I made and fixed while writing this: my first patch referenced `b_gen`/`t_gen`, which do not exist
(`t_gen` is a timestamp). The real accumulators are `bgs`/`tgs` inside the generation loop, and the texts
were not being kept at all — so the per-dataset F1 had nothing to pair against. Both are now explicit.
